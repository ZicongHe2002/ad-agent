# 网页评论与开放 API 调研（2026-09-19）

普通用户通过网页评论，技术上不需要申请开发者 API；它依赖平台自己的网页、正常登录会话和该账号当前拥有的评论权限。浏览器自动点击同一界面是另一种实现方式，但能操作页面不代表平台允许自动操作，也不代表可以稳定批量推广。

本项目目前没有实现小红书或抖音的真实浏览器评论发送。现有真实平台适配器也未接通顶层评论发布，不能把 Mock 成功或人工核对状态描述为真实平台已接通。

## 推荐的实现与验证顺序

1. **先验证正常人工路径。** 由账号本人在专用、可见的浏览器会话中正常登录，确认目标作品开放评论、账号没有禁言，并区分作品主评论输入框与某条评论的回复框。首次登录、短信、二维码、验证码和风险核验均由本人完成。仅使用取得合法使用权限的账号；用户授权软件操作自己的会话与平台是否允许自动化需要分别确认。
2. **测试期逐条审核。** 系统生成候选内容，用户核对账号、目标作品、完整文案、品牌身份和所需披露，再人工发送并登记结果。先验证整个业务闭环，而不是用未经测试的选择器宣布浏览器发送已经可用。
3. **浏览器适配器作为独立通道。** 若后续确认平台条款及授权允许，并完成账号与页面实测，可实现明确选择的可见网页交互通道。账号绑定专用会话，只通过实际观察到的正常界面操作；不读取、复制或日志化会话秘密，不模拟私有接口，不隐藏自动化、不绕过核验。官方 API 不可用时不能悄悄改用网页发送。
4. **推广期自动执行有前提。** 用户明确启用目标账号和活动；平台许可、账号状态、页面定位、内容质量、披露、频率预算、重复检测和停止开关全部通过后，才允许无人逐条确认的执行。抖音当前普通协议的自动化限制是现实阻碍，不能仅凭技术可行宣布这一通道可投入自动推广。
5. **异常立即暂停。** 登录失效、验证码、风险验证、限流、禁言、评论关闭、目标或账号变化、页面结构变化时停止该账号任务并转人工处理；不更换账号或网络绕过限制，不自动解验证码。

## 如何判断发送结果

以下是未来需要实测的验收标准，不是本轮观察到的平台保证：

- 发送前记录账号、目标作品 URL、完整最终文本、内容摘要、本地意图 ID 和发送时间；每个意图只允许一个执行者。
- 点击成功或输入框清空不足以认定发布成功。需要在目标作品正常评论界面中核对本账号、新发送的完整文本及作品归属；页面若提供稳定评论 ID 或可访问链接，应一并保存。
- 页面提示待审核时单独记录待审核，不能标成所有人可见；当前账号可见也不等于其他用户可见。刷新后正常界面仍能找到对应评论，比单次乐观插入更有证明力。
- 点击后断线、超时或页面崩溃记为 `PUBLISH_UNCERTAIN`。先通过正常页面核查原账号、原作品、原文案和发送时段；找不到可能只是审核或显示延迟，不自动据此再次发送。无法确定时交人工核对，避免重复评论。

项目原有 `NON_GOALS.md` 与能力文档体现此前的实现范围。它们不是“普通网页操作在技术上不可能”或外部系统一律禁止研究的证据。本调研单独分析用户提出的新方向；当前交付仍保留明确的官方接口/人工发布边界，浏览器发送需要后续实测与独立实现。
